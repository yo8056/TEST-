# 補貨檢查

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「數字一定要從盤點資料抄，不能自己編」，而且每個數字都要能驗算。

## 什麼時候用

- 跑完 `npm run simulate`，要決定下一版策略每樣菜備幾份時
- 在瀏覽器玩完一天，想看「倉庫盤點」頁的結果該怎麼調整時

## 資料從哪裡來

在 `web-lab` 資料夾執行：

```text
npm run simulate -- plans/策略檔.json --json
```

每一天的 `inventory` 欄位，是那天每樣上架的菜的盤點：

| 欄位 | 意思 | 怎麼驗算 |
|---|---|---|
| `name` | 菜名 | — |
| `stocked` | 早上備了幾份 | 策略檔裡的 `qty` |
| `sold` | 賣出幾份 | 打烊報表 |
| `waste` | 報廢幾份 | 備貨 − 賣出 |
| `missed` | 賣完之後，還有幾位客人想買卻沒買到 | 客人卡片上「賣完了」的數量 |
| `status` | `ok` 正常、`out` 缺貨、`over` 報廢過多 | 規則書「倉庫盤點」 |
| `suggest` | 明天建議備幾份 | 賣出 ＋ 沒買到 |

## 步驟

1. 執行上面的指令，讀每一天的 `inventory`
2. 先驗算：`waste` 有沒有等於 `stocked − sold`？對不上就停下來回報，**不要用錯的資料做建議**
   - ★ 我補充的驗算：每個數字都要是 0 以上的整數、`sold` 不能超過 `stocked`；再照規則書核對 `status`（沒買到 > 0 是缺貨、報廢 ≥ 5 是報廢過多、其他正常）和 `suggest`（＝賣出 ＋ 沒買到）。資料缺漏或互相矛盾時，指出是哪一天、哪樣菜、哪個欄位，並停止提出那一筆的備貨建議。理由：錯的資料算出來的建議一定錯，先擋下來比事後修便宜。
3. 挑出 `status` 不是 `ok` 的菜
4. ★ 建議備貨量要不要再調整（例如：明天客人比較多的日子，要不要多備幾份？多備幾份？）：
   - 只針對缺貨或報廢過多的菜提出調整。**基礎建議量＝賣出 ＋ 賣完後沒買到**（規則書的算法），每個數字都要列出算式。
   - 回報時分成兩行：「依今天資料算出的基礎建議」和「考慮隔日條件後的調整」。隔日條件只有三種可以用：隔天開店星等的倍率、隔天要花的宣傳費倍率（200 元 +20%、500 元 +45%）、遊戲預告明講的天氣或事件；調整量＝基礎建議 × 倍率後四捨五入，寫出算式。
   - 沒有隔日需求的證據時，就用基礎建議量，不自行多加固定百分比。理由：多備的每一份都先付成本，賣不掉還要付清潔費；沒有證據的加量等於賭。
   - 報廢過多的菜：建議量就是基礎建議量（等於賣出量）；算出來是 0 份時，建議那天先不上架這樣菜，把名額讓給有人想買的菜。
   - 每一筆建議都附「建議備貨成本」＝建議份數 × 規則書的單份成本，列出算式。
   - 要判斷整份備貨能不能執行，必須一起看：所有菜合計份數（≤ 80）、總成本、宣傳費、當天可用資金。少了任何一項資料，就寫「尚無法確認可執行性」，不把單一樣菜的建議當成已驗證的完整策略。
5. ★ 同一樣菜連續幾天都缺貨或報廢過多，要怎麼提醒：
   - 同一樣菜**連續兩天以上**缺貨或報廢過多，在回報裡加一行「持續現象」，列出各天的備貨、賣出、報廢、沒買到。
   - 只有一天的資料時，不推測多天趨勢，只寫「只有一天資料，無法判斷是否持續」。理由：一天可能是天氣或事件造成，連續兩天才值得當成結構問題處理。
6. 用下面的回報格式回報

## 回報格式

```text
策略檔：
驗算結果：通過 / 第 N 天的 ○○ 對不上（寫出哪個數字）
第 N 天：
  缺貨：菜名 備 … 賣 … 沒買到 … → 建議 …
  報廢過多：菜名 備 … 賣 … 報廢 … → 建議 …
★ 我想多看一個欄位：建議備貨成本（建議份數 × 單份成本，列出算式）；以及「可執行性」（合計份數、總成本、宣傳費、可用資金，缺資料就寫「尚無法確認可執行性」）
下一版每天建議的備貨量：
```
