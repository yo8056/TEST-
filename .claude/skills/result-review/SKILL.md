# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | ★ 備貨超過當天實際想買的人數；16 份以上還會多付 50 元大型廚餘清運費（實際觀察：看盤點的報廢欄；原因是推測時要標示） | ★ 用 reorder-check 的基礎建議量（賣出 ＋ 沒買到）調降那樣菜；建議量是 0 就先不上架 |
| 嫌太貴很多 | ★ 定價超過這些客人剩下的預算（實際觀察只有人數；是哪樣菜太貴屬於推測，要標示） | ★ 照 pricing-rules 挑一樣菜降價測試，寫出降多少、每份少收多少；一次只降一樣才看得出效果 |
| 想吃的沒上架很多 | ★ 上架的四樣沒有涵蓋當天客人想吃的菜（哪一樣沒涵蓋要從客人說的話確認，否則是推測） | ★ 把連續報廢過多、賣最少的那樣菜換成客人想吃的菜；最多 4 樣、合計最多 80 份 |
| 因為討厭的菜不進門 | ★ 上架了某些客人討厭的菜，這些客人連門都不進，也不留評價 | ★ 比較那樣菜的賣出量和不進門人數：賣得少、擋掉的人多就下架或換菜；賣得多就保留並寫出取捨 |
| 星等往下掉 | ★ 當天滿意的人 < 30% 或不滿的人 ≥ 25%（規則書的星等表）；不滿來自什麼都沒買到，滿意要價格 ≤ 建議售價 | ★ 先處理讓人空手而回的原因（缺貨補貨、沒上架換菜、太貴降價），價格壓回建議售價以內；隔天來客會因星等變少，備貨要一起下修 |
| ★ 我自己發現的現象：宣傳後增加來客，但淨利未改善 | ★ 新增的收入不夠付宣傳費和多備的成本，或多來的客人買不到（缺貨、太貴、沒上架） | ★ 先核對三個數字：新增收入、新增備貨成本、宣傳費；新增收入 − 新增成本 < 宣傳費就取消或降一級宣傳，或先補足缺貨的菜再宣傳 |

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
   - ★ 我補充：回報時把「實際觀察」（試算結果裡看得到的數字，寫出第幾天、哪樣菜）和「推測」（可能原因）分開寫，推測要標示成推測；修改要列出修改前後的數值，並確認符合資金、合計 80 份、最多 4 樣的限制
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
